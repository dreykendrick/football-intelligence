# Historical Dataset Releases & Scientific Assembly

This document defines the architecture, versioning model, quality gates, selection policy, fingerprint determinism, and CLI interface for **Historical Dataset Releases** in the Football Intelligence & Probability System.

---

## 1. Core Principle

The canonical PostgreSQL database may contain multiple seasons, failed imports, partial imports, experimental sources, and future additions. 

**Downstream feature engineering and model training must NOT query arbitrary PostgreSQL matches directly.**

Instead, downstream scientific workflows consume an **Approved Historical Dataset Release** with explicit, immutable membership.

```text
Canonical Historical DB
      ↓
Quality (Sprint 2.4) + Identity Gates (Sprint 2.3)
      ↓
Selection Policy (`mvp_a_recent_3_usable_seasons_v1`)
      ↓
Dataset Membership (Seasons & Matches)
      ↓
Source Version Locking (SHA-256)
      ↓
Deterministic Fingerprint Calculation
      ↓
Validation & Warning Acceptance
      ↓
APPROVED HISTORICAL DATASET RELEASE (`mvp_a_historical_v1`)
```

---

## 2. Release Lifecycle

A dataset release transitions through explicit status states:

1. **`DRAFT`**: Candidate dataset release generated by the build engine. Open for inspection and validation.
2. **`VALIDATING`**: Undergoing pre-approval validation checks.
3. **`APPROVED`**: Officially validated, locked, and **strictly immutable**. Only APPROVED releases are consumed by production feature engineering and model evaluation workflows.
4. **`SUPERSEDED`**: Replaced by a newer dataset release version (e.g., `v1` superseded by `v2`). Retained for auditing past model experiments.
5. **`RETIRED`**: Archived and no longer eligible for active model backtesting.
6. **`FAILED`**: Rejected due to validation blockers or unhandled errors.

---

## 3. Immutability & Versioning

Once a dataset release is **APPROVED**:

* Scientific membership (included seasons, matches, team references) is **strictly immutable**.
* No matches or seasons can be added, modified, or removed in place.
* Data corrections or historical source updates require creating a new version (e.g., `v2`).
* Versions use human-readable semantic identifiers (e.g. `mvp_a_historical_v1`).

---

## 4. Quality & Warning Acceptance Policy

* **`BLOCKED` Seasons**: Any competition-season bearing a `BLOCKED` Sprint 2.4 quality status is strictly prohibited from entering an approved dataset release.
* **`READY_WITH_WARNINGS` Seasons**: Seasons bearing non-blocking warnings require explicit documented limitation acceptance strings during approval (e.g., `"Kickoff times default to 12:00 UTC (date-only precision)"`).

---

## 5. Dataset Fingerprint Determinism

Every dataset release computes a 64-character SHA-256 fingerprint from:

1. Release key and version.
2. Selection policy key and version.
3. Sorted competition-season tuples `(comp_code, season_year, source_checksum)`.
4. Sorted match tuples `(match_id, kickoff_utc, home_team_id, away_team_id, home_score, away_score, raw_source_checksum)`.

Volatile metadata (build timestamp, database surrogate primary keys) is explicitly excluded, ensuring 100% environment reproducibility.

---

## 6. Developer CLI Reference

```bash
# List all dataset releases
python scripts/historical_dataset.py list

# Build candidate release (DRAFT)
python scripts/historical_dataset.py build --dataset mvp_a_historical --version v1

# Validate candidate release
python scripts/historical_dataset.py validate --dataset mvp_a_historical --version v1

# Approve validated candidate release
python scripts/historical_dataset.py approve --dataset mvp_a_historical --version v1 --accept-warning "Kickoff times default to 12:00 UTC (date-only precision)"

# Verify locked fingerprint against database state
python scripts/historical_dataset.py verify --dataset mvp_a_historical --version v1

# Output detailed release report
python scripts/historical_dataset.py report --dataset mvp_a_historical --version v1
```
