# 4. Mathematical Model

Implement a regularized log-linear Attack–Defence Poisson model.

For a fixture where home team \(i\) plays away team \(j\):

$$
G_H \sim \text{Poisson}(\lambda_H)
$$

$$
G_A \sim \text{Poisson}(\lambda_A)
$$

Use a formulation equivalent to:

$$
\log(\lambda_H)
=
\mu_c + h_c + \alpha_{i,c} - \delta_{j,c}
$$

$$
\log(\lambda_A)
=
\mu_c + \alpha_{j,c} - \delta_{i,c}
$$

Where:

* \(c\) is the competition
* \(\mu_c\) is the competition scoring baseline
* \(h_c\) is home advantage
* \(\alpha_{team,c}\) is attacking strength
* \(\delta_{team,c}\) is defensive resistance or defensive strength

If the repository uses a convention where larger defence parameters mean weaker defence, adjust the signs accordingly. Use one documented convention consistently throughout training, prediction, artifacts and explanations.

The model must make the interpretation unambiguous.

For example:

```text
attack_strength > 0     => stronger-than-average attack
defence_strength > 0    => stronger-than-average defence
```

or:

```text
defence_weakness > 0    => weaker-than-average defence
```

Do not mix these conventions.

* Parameter estimates must be deterministic for identical data and configuration.
* Artifact loading must preserve identical parameter interpretation.
* Unit tests must verify the constraints within a documented tolerance.
* Competition baselines must not be accidentally duplicated inside team parameters.

Do not solve identifiability by arbitrarily dropping undocumented parameters.
